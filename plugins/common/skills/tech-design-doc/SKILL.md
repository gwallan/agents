# 技术设计文档生成

## 目标

将需求文档、接口文档与用户提供的技术设计模板整理为可直接交付的技术设计文档。输出时必须遵循模板结构，并补齐页面与接口对应关系、展示字段与接口字段对应关系、状态映射、实现位置、架构图与注意事项。

## 工作流

### 1. 先确认当前应用

- 如果当前项目刚才下包含多个应用，需要先判断当前 web 应用属于哪一个
- 如果上下文已经明确，则直接沿用
- 如果不明确，优先根据 PRD、接口文档、页面名、路径名和术语判断；仍不明确时，先看应用所属路径下的 `AGENTS.md` 和 `docs/index.md`，不要猜
- 只使用当前应用对应的文档与术语，不混用另一个应用的页面、路径和字段命名

### 2. 先确认上下文

- 优先读取当前 Web 应用的 `AGENTS.md`
- 读取 `docs/index.md`，再按需读取 `glossary.md`、`decisions.md`
- 读取用户提供的 PRD、API 文档与技术设计模板
- **MANDATORY - READ ENTIRE FILE**: 生成前必须完整读取 `@/references/tech-design-template.md`，不要只看标题、目录或片段

### 3. 深度理解实现

- 如果文档涉及具体实现位置，先定位实际源码和至少一个调用点，再写路径、职责与修改范围
- 新增文件、修改文件、实现位置都必须以仓库中的真实文件为准
- 如果当前材料没有源码或不需要改代码，明确写「本期不修改」，不要虚构实现路径

### 4. 统一术语与范围

- 统一功能名、对象名、状态名与禁用词
- 优先采用术语表；没有明确来源时沿用用户原词，不自行发明新词
- 区分页面级对象、目录对象、任务对象与预览结果
- 仅覆盖当前文档明确要求的范围，不补充未要求的能力

### 5. 按模板输出

必须按用户提供的技术设计模板组织内容，保持以下结构顺序：

1. 实现概述
2. 实现位置
3. 核心实现
4. 架构设计
5. 关键技术详解
6. 调试指南
7. 注意事项
8. 后续优化方向

- 模板内容保存在 `@/references/tech-design-template.md`
- 生成最终文档时优先对照该模板的章节、措辞和信息组织方式
- 页面与接口对应关系、展示字段与接口字段对应关系、状态文案与后端枚举对应关系，必须补齐为表格或明确映射
- 没有实际内容的章节直接写「本期不涉及」，不要留空

### 6. 文件级描述

- 新增文件写清路径、职责与作用
- 修改文件只写本期实际会改的文件
- 如果某个现有文件本期不修改，明确标记「本期不修改」

### 7. 输出前自检

- 当前 web 应用是否已确定，并且没有混用另一个应用的术语
- PRD、API 文档、术语表、技术设计模板是否已经读取
- 每个页面、接口、字段、状态是否都能找到来源
- 所有无法确认的内容是否已经写成「待确认」
- 所有没有实际内容的章节是否已经写成「本期不涉及」

## NEVER

- NEVER 编造接口路径、字段名、后端枚举、文件路径或实现类名；没有来源就写「待确认」
- NEVER 脱离 PRD 扩写功能、页面、流程或异常分支
- NEVER 把映射关系写成纯叙述，必须能直接核对
- NEVER 在 Mermaid 语法不确定时硬输出图；改用文本流程
- NEVER 混用 `platform` 与 `assets` 的路径、页面名和术语
- NEVER 把通用背景、教程或实现之外的推测塞进文档
- NEVER 把没有内容的章节留空；改写成「本期不涉及」

## 输出要求

- 使用中文
- 保持结构化、可扫读
- 使用直角引号「」描述可见文案
- 不扩写无关背景，不加入实现之外的推测
- Mermaid 图仅在语法确定时输出

## 校验清单

- 需求范围是否与 PRD 一致
- 接口字段是否与 API 文档一致
- 页面与接口是否有一一对应说明
- 展示字段是否有明确来源字段
- 本期修改文件是否与实际范围一致
